# Agent 对弈室

Agent 对弈室面向同一台电脑上的本地 Codex、Claude Code、DeepSeek Harness、Kimi Code、OpenCode 等 agent。一个本地服务维护棋局，选手通过 MCP 或 CLI 操作，用户在浏览器观看落子、棋手随想和独立解说。产品入口与可复制的启动提示见[根目录 README](../../README.md)。

## 分支与目录

`arena` 是独立长期发行渠道，接受从 `dev` 同步的共享游戏更新。对局服务、MCP、CLI、观战界面与本产品 Skill 留在该渠道；不会因其代码可复用就要求合入 `dev`。本产品开发从 `arena` 新建独立任务分支/worktree，经实现、验证、本地预览与用户确认后合回 `arena`。用户从 [GitHub 的 arena 分支](https://github.com/YinkaiYu/topology-gomoku/tree/arena)获取本产品。

原游戏规则、内置 AI 与资源沿用 `app/`，不复制一套变体。发现原游戏共有的缺陷时，另建 `dev` 任务处理，再同步修复。游戏 SemVer 继续跟随共享基线；对弈室能力不自行递增原游戏版本。记录比赛时保存游戏版本，避免混淆不同规则版本。

| 路径 | 用途 |
| --- | --- |
| `arena/server.cjs` | 仅监听本机的 HTTP 服务、观战资源、调用入口 |
| `arena/mcp.cjs` | stdio MCP 桥接；各客户端连接同一个服务 |
| `arena/cli.cjs` | 启动、检查、停止、调用工具与生成客户端配置 |
| `arena/prompts/` | 可直接修改的角色邀请、选手/解说提示、MCP 指令、工具描述和规则说明 |
| `arena/skills/topology-gomoku-arena/SKILL.md` | 主持、选手与解说的使用流程 |
| `.arena/` | 本地运行记录、日志、棋局数据与临时请求，全部忽略 Git |

## 环境与启动

需要 Node.js 20 或更新版本及 npm。安装运行依赖后，日常启动不需要重新安装：

```sh
npm ci --prefix arena
node arena/cli.cjs up
```

`up` 在后台启动服务，等待健康检查通过，再打开普通本地浏览器地址。再次执行会检查服务名称、当前 checkout 路径与进程记录，只有全部一致才复用。服务独立于发起 agent 会话存活。解说默认关闭；主持人只有收到用户的解说邀请后才转任解说员。

```sh
node arena/cli.cjs up --port 4319 --no-open
node arena/cli.cjs status
node arena/cli.cjs stop
```

默认端口为 4318；已有服务时沿用该 checkout 的运行记录。更换端口前停止本 checkout 的旧服务。端口属于其他服务时，选择其他端口，不结束占用进程。`stop` 通过房主凭证和匹配的运行记录请求关闭，不根据任意 PID 杀进程。

`.arena/runtime.json` 保存运行地址、进程、checkout 路径和房主 token；`.arena/server.log` 保存启动日志。浏览器只有一个入口，不区分房主与观战链接。`/api/bootstrap` 为本地浏览器设置 HttpOnly、SameSite=Strict 的管理会话，地址栏和页面脚本不接收管理 token。CLI 仍通过运行记录认证管理操作，MCP 只公开角色工具。服务核验 Host、Origin 和跨站请求；启动与 status 不输出凭证。只把对应角色邀请发给选手，不分享运行记录。

服务仅支持 HTTP loopback 地址。原生 Windows、macOS、Linux 的本地 agent 可通过同一地址连接；WSL、容器、SSH 或客户端沙箱可能拥有不同网络边界，需先确认能访问该 loopback 服务。不要通过绑定 `0.0.0.0`、公网隧道或开放局域网端口来绕过本产品的本地范围。

## MCP 配置

用户先按 README 的启动提示准备服务，再把 README 中的接入提示发给各个参赛客户端；完成配置与必要的重载后，才创建比赛并发送席位邀请。配置独立于棋局，不需要邀请凭证。`/api/health` 返回服务标识和 `workspacePath`，供接入 agent 找到现有代码；无需重新下载或另开服务。

在该仓库目录生成适用于当前客户端的配置片段；地址不同于默认值时追加 `--url 服务地址`：

```sh
node arena/cli.cjs mcp-config codex
node arena/cli.cjs mcp-config claude
node arena/cli.cjs mcp-config kimi
node arena/cli.cjs mcp-config opencode
node arena/cli.cjs mcp-config deepseek
```

每条命令只输出对应片段，不修改客户端配置。片段使用实际 Node 可执行文件、当前 checkout 的绝对桥接路径与服务地址；移动 checkout 或改端口后应重新生成。不要将这些本机路径提交到 Git。所有 stdio 子进程只是桥接，客户端关闭它们不会销毁共享棋局。

更新工具 schema 或工具说明后，除重启 HTTP 服务，还需让各客户端重启 stdio MCP 连接并重新发现工具。桥接进程在启动时加载 `tools.cjs`，不会因后台服务重启而自动更新；因此旧桥接可能继续拒绝已经被新版服务接受的字母坐标。地址与 checkout 未改变时无需重写配置。参赛文件也需由 agent 重新读取。

| 客户端 | 片段位置与格式 |
| --- | --- |
| Codex | `.codex/config.toml` 或用户配置中的 `[mcp_servers.topology-gomoku-arena]` |
| Claude Code | 当前项目的本地 MCP 配置，或项目 `.mcp.json` 的 `mcpServers` 条目 |
| Kimi Code | 项目 `.kimi-code/mcp.json` 或该版本支持的 MCP 配置中的 `mcpServers` 条目 |
| OpenCode | `opencode.json` / `opencode.jsonc` 的 `mcp` 条目 |
| DeepSeek Harness | 当前 profile 的 `@deepseek-ai/dsh-mcp-client` YAML 插件配置条目 |

Agent 获得用户的配置请求后，应读取当前客户端实际加载的配置，只合并该服务条目，保留其余配置和注释。下载目录不一定是客户端的项目目录，同一客户端的不同项目也可能使用不同配置。不要整文件覆盖，不替用户改变权限策略。需要重载或重启时，说明修改位置与具体步骤，结束接入任务；用户完成后再发送入席邀请。不自动改用 CLI，CLI 仅供用户明确选择。已有连接可复用，不要求每局重新配置。

格式核对来源：[Codex MCP](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)、[Claude Code MCP](https://code.claude.com/docs/en/mcp)、[Kimi Code MCP](https://www.kimi.com/code/docs/en/kimi-code-cli/customization/mcp.html)、[OpenCode MCP](https://opencode.ai/docs/mcp-servers/)、[DeepSeek Harness MCP client](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/mcp/mcp-client/README.md)。配置兼容性与完整客户端实测是两回事；本地协议验证不能当作五个客户端均已完整对弈的证据。

Skill 不要求预先安装到客户端。启动 prompt 和角色邀请可以要求 agent 直接读取仓库里的 [Skill](../../arena/skills/topology-gomoku-arena/SKILL.md)。用户希望长期安装时，再按各客户端支持的 Skill 位置安装；不为一次对局自动改所有客户端。

## CLI 调用

CLI 与 MCP 调用同一对局逻辑。十个 MCP 工具为 `arena_join`、`arena_ready`、`arena_state`、`arena_move`、`arena_resign`、`arena_draw`、`arena_note`、`arena_rules`、`arena_wait`、`arena_replay`。CLI 还可调用公开的 `arena_catalog`、`arena_list`，以及管理工具 `arena_create`、`arena_invite`、`arena_control`、`arena_profile`、`arena_delete`、`arena_clear`。房主工具会核对当前 checkout 的运行记录并附加房主凭证；选手调用仅传自己的席位 token。

建议将请求保存为 `.arena/request.json`，再调用：

```sh
node arena/cli.cjs call arena_state --file .arena/request.json
```

示例请求体：

```json
{
  "gameId": "从邀请获取",
  "token": "从加入结果获取"
}
```

也支持 `--json -` 从 stdin 读取，或 `--json JSON`。跨 shell 自动化优先使用 UTF-8 文件，避免引号、中文、反引号或 `$` 被 shell 解释。调用另一端口加 `--url http://127.0.0.1:4319`。成功输出 `{ "ok": true, "result": ... }`；失败写入结构化错误并以非零状态退出。不要把错误字符串当成成功落子。

`arena_move` 使用最新棋局 `expectedVersion` 与唯一 `requestId`，网络超时重试同一动作时保留 requestId。随想使用独立事件序号，不应让棋盘版本变化。`arena_wait` 使用 `afterSeq` 等待后续事件，单次最长 25 秒，避免高频轮询。每次读取新状态后更新棋局版本，事件分页游标使用 `nextAfterSeq`；初始游标取加入状态的 `eventSeq`。

棋手入席后持续参与至终局、用户要求停止或无法恢复的错误，不以“我会等待”结束会话。对手行棋时可分析与发随想，并交替读取新状态；长时间准备后刷新局面，避免沿用旧落点。等待超时只是一次轮询结束，不代表比赛结束；误在自己的行棋回合调用 `arena_wait` 时立即返回，不挂起消耗余时。此改进不能唤醒已结束的客户端会话，也不替客户端执行后台分析。

常用参数如下；加入结果为 `{token, role, state, rules}`，后续状态包含 `version`（棋局版本）、`eventSeq`（所有事件序号）、`ply`（已落子手数）、`turn`、`phase`、`playPolicy`、`preparation`、`clock`、`legalCells` 与行优先的一维 `board`。观众坐标从左下角 A1 开始：横轴 A、B、C……向右递增（不跳过 I），纵轴 1、2、3……向上递增。工具的 `cell` 可直接传 `"A1"`；旧数字索引仍为从左上角开始的 `cell = y * width + x`，对应标号行数为 `height - y`。黑子为 1，白子为 -1，空位为 0，落子与路径结果附带可读坐标。

| 操作 | 参数 |
| --- | --- |
| `arena_create` | `topology`、`mode: "ai" / "duel"`，可选 `playPolicy: "direct" / "assisted"`、`title`、`difficulty`、`width`、`height`、`clock: {initialMs, incrementMs}`（`null` 不计时）、`players: {black: {name, avatar}, white: {name, avatar}}` |
| `arena_profile` | `gameId`、`role: "black" / "white"`、`name`、`avatar`；修改显示资料，不改变席位凭证 |
| `arena_delete` | `gameId`；只删除已结束的棋局 |
| `arena_clear` | 无参数；清空已结束棋局，保留等待/进行/暂停的棋局 |
| `arena_invite` | `gameId`、`role: "black" / "white" / "commentator"` |
| `arena_join` | `gameId`、`inviteToken`、`name`，可选 `model` |
| `arena_ready` | `gameId`、自己的 `token`；准备完成后确认就绪，重复调用幂等 |
| `arena_state` | `gameId`、自己的 `token`，可选 `afterSeq`、`limit` 查询增量事件 |
| `arena_replay` | `gameId`、自己的 `token`，`afterSeq` 默认 0，`limit` 默认 20、最大 50 |
| `arena_rules` | `gameId`、`token`；可选 `cell`、`direction`、`length` 查询路径 |
| `arena_move` | `gameId`、`token`、`cell`、`expectedVersion`、`requestId` |
| `arena_resign` | `gameId`、`token`、`expectedVersion`、`requestId` |
| `arena_draw` | `gameId`、`token`、`expectedVersion`、`requestId`、`action: "offer" / "accept" / "decline" / "withdraw"`；回应/撤回需要 `offerId` |
| `arena_note` | `gameId`、`token`、`text`、所评局面的 `ply`、唯一 `requestId` |
| `arena_wait` | `gameId`、`token`、`afterSeq`、`timeoutMs`，可选 `limit`（默认 20、最大 50） |
| `arena_control` | `gameId`、`action: "start" / "pause" / "resume" / "stop" / "disqualify" / "commentary_on" / "commentary_off"`；`disqualify` 另传违规方 `role: "black" / "white"` |

拓扑使用 `arena_catalog` 返回的标识；内置 AI 固定执白。棋手随想和解说统一通过 `arena_note` 发送，角色由席位 token 确定，不传 `kind`。消息可关联当前或历史局面，不限制己方回合，等待开赛、暂停与终局后也可发送；解说仍受开关控制。每条最多 1000 字符，不设每个局面的条数上限，让棋手将即时想法逐句发送。消息与落子共用 requestId 去重机制，重试不新增气泡，服务重启后仍有效。

### 棋手响应与事件分页

棋手和解说员携带席位 token 时，日常状态仅包含当前棋盘、合法落点、最新一手、棋局进度、准备倒计时、棋钟、就绪状态及当前结果。席位资料只含姓名、模型、显示名和入席／就绪标记，全部响应均不携带头像。观战页面继续使用完整资料、事件与棋谱，头像上传和聊天显示保留。

`arena_state` 默认不返回事件和落子历史；传 `afterSeq` 时，与 `arena_wait` 一样返回后续可见事件页。每页默认 20 条、最多 50 条，并限制事件内容为 16 KiB。`eventSeq` 是棋局最新序号，`nextAfterSeq` 是本页已扫描位置，`hasMore` 表示还有事件可读。下一页使用 `nextAfterSeq`，避免跳过尚未读取的事件。棋盘始终是最新局面，不随事件分页回退；轮到己方时优先行动，再按需查询历史。

日常增量中的自身随想只返回事件标识，原文可通过 `arena_replay` 按需分页读取。复盘默认从 `afterSeq: 0` 开始，沿同一游标机制取后续页；落子事件附坐标，不另附重复的全局 `moves` 数组。其他席位的随想与解说继续按角色过滤，资料变更事件也不携带头像。

`arena_note` 返回 `{event, state}`：`event` 为原事件的序号、类型、角色和手数，`state` 为最新进度、余时、提和及结果摘要；不重复返回原文、棋盘或历史。重试同一请求保留原事件标识，刷新当前余时。发言回执不推进已读历史游标。落子回执保留最新棋盘与余时，不重复棋谱和聊天。

CLI、stdio MCP 和 HTTP MCP 使用相同的棋手数据投影。CLI 的 `call` 输出紧凑单行 JSON，避免将棋盘数组展开成数百行。MCP 保留文本结果与结构化结果两个标准字段以供不同客户端读取，二者均使用精简数据。更新后重启服务、重连 MCP 并重新读取 Skill，以加载分页参数和新响应约定。

### 规则与路径查询

入席结果的 `rules` 与不传路径参数的 `arena_rules` 包含本局的 `briefing`：当前尺寸、边界连接、完整单步映射定义、单步示例，以及一条由不同交点组成的连续线路。`definition` 写明坐标范围、方向向量、越界条件、映射公式、执行顺序和无连接时的 `null`；覆盖直线、斜线与角点同时跨边。公式使用与引擎一致的左上角零基坐标，并明确换算到观众坐标：`A1` 对应 `(0, H−1)`，字母列号为 `x+1`，标号行数为 `H−y`。

定义与说明集中在 `arena/prompts/topology.json`，每次只返回本局拓扑；参数使用本局实际尺寸。坐标、方向示例和连续线路由共享裁判引擎生成。运行时只将定义作为说明返回，不另设裁判；测试解释实际返回的公式，逐格、逐方向核对共享裁判，防止说明与实现分离。

例如 7×7 莫比乌斯棋盘，`G6` 向右接到 `A2`；`G6` 向右上接到 `A1`，接下来沿右下继续。`B7` 向上则返回 `to: null`，明确表示该步没有连接。棋手可直接依据说明理解棋盘，需要核对具体线路时再查询；这些示例只解释几何，不推荐落点。

`arena_rules` 每次都返回精简的 `state: {gameId, phase, turn, ply, version, eventSeq}`，与同一时刻 `arena_state` 的相应字段一致。等待、暂停时的 `turn` 表示下一位棋手，只有 `phase: "playing"` 才能落子；终局后 `turn` 为 `null`。此摘要不含棋盘、事件或任何席位的随想，需要当前局面时调用 `arena_state`。

查询路径时只返回几何结果、尺寸与方向定义、当前进度和余时，不重复整套规则说明。查询时同时提供 `cell`、`direction`，`length` 是包含起点在内的不同交点数量，默认取 `target`，最大为当前棋盘交点数。MCP 与 CLI 使用相同范围。返回：

- `path.cells`、`path.directions`：按顺序保留实际经过的不同交点和各处的前进方向；跨接缝后的方向可能改变。
- `path.coordinates` 与 `cells` 一一对应；`next`、`stop` 及 `stop.next` 中的 `coordinate` 与同对象的数字 `cell` 对应。
- `path.seams[i]`：从 `cells[i]` 到 `cells[i+1]` 的接缝位标记。
- `path.requestedLength`、`path.complete`：请求长度及是否走满。几何查询忽略棋子，不判断是否连五。
- `path.stop`：走满时为 `null`；否则为 `{reason, cell, direction, next}`。`boundary` 表示从最后交点继续会越过未连接的边界，`next` 为 `null`；`repeated_cell` 表示下一步会重访已有交点，`next` 给出该步的交点、方向和接缝，但不将它追加到路径中。
- 顶层 `next`：始终是从请求起点出发的一步，与请求长度无关，不是从路径终点出发的一步。因此单步可走和长路径走不满可以同时成立。

例如在 7×7 莫比乌斯棋盘，从 `cell: 0` 向南（`direction: 2`）查询 `length: 8`，得到 `cells: [0,7,14,21,28,35,42]`、`complete: false`、`stop.reason: "boundary"`，而顶层 `next.cell` 仍为 `7`。从中行 `cell: 24` 向东查询 9 个交点，则在经过 7 个不同交点后返回 `repeated_cell`，下一步将回到 `24`。这两种结果都不是规则出错。

接口兼容说明：此前走不满的查询返回 `path: null`，现在始终返回路径对象，调用者应以 `path.complete` 判断是否取得请求长度，不能只检查 `path` 是否存在。原有成功路径的三个数组与顶层 `next` 含义不变。规则计算和胜负判定仍使用共享引擎；更新服务后重连 MCP 以读取新的工具说明。进行中的比赛可继续使用旧服务，结束后再更新重启。

## 比赛与棋手随想

默认先按 README 完成服务启动与各客户端的 MCP 接入，再在浏览器创建比赛、从设置复制角色邀请。双方入席后统一开始准备倒计时；双方提前就绪或准备到时自动开赛。单 agent 对内置 AI 只有一个外部选手，内置 AI 已就绪；双 agent 局分别邀请黑白双方。解说默认关闭，页面不显示解说区，也不为其保留空白。用户主动从设置面板取得解说邀请时开启；加入或离开不阻塞比赛。设置中可再次关闭或开启，关闭会阻止新的解说发言，但保留已有记录。解说 agent 看到 `commentaryEnabled: false` 后停止解说，等待用户再次邀请。

新棋局的 `playPolicy` 固定为 `direct`（默认，仅允许推理）或 `assisted`（允许自制工具/引擎），分别有 1 分钟和 5 分钟准备时间。创建后不可修改。入席结果和规则接口返回 `playPolicyRule` 与 `preparationRule`，明确允许的接口、工具开发边界、违规判负及自动开赛条件。仅允许推理仍可使用全部正常对弈室接口；自制棋盘建模、枚举、评估与搜索程序均属于工具模式。工具模式从双方入席、统一准备倒计时开始后允许开发和运行本局自制程序。

入席与就绪分离：`seats.black/white.ready` 表示各自确认完成准备。准备期间保持 `phase: "waiting"`，行棋棋钟 `active: null`；双方入席后开始独立的准备倒计时。`preparation` 返回 `durationMs`、`startedAt`、`deadline`、`remainingMs`、`serverNow` 和 `completedAt`；倒计时运行期间提供 `deadline` 与 `serverNow`，开始前和完成后两者为 `null`，`completedAt` 记录开赛时刻。时间戳均为 Unix 毫秒，不限时棋局同样执行准备时限。双方提前确认就绪立即开赛，到达截止时间自动开赛，黑方棋钟以准备截止时刻为起点，即使服务调度稍晚也不额外赠时。重复确认与重连不会延长准备时间或重复开赛；自动开赛后的 `arena_ready` 返回当前状态，保留实际就绪记录。房主无法代替棋手就绪。

工具使用属于比赛约定，本服务不监控客户端本地进程。确认违规后，房主通过设置里的违规判负操作，或管理接口 `arena_control` 的 `disqualify` 动作裁定；对方获胜，`winReason: "rule_violation"`，停止棋钟并保存结果。棋手凭证没有裁定权限，已结束棋局不能改判。

所有进行中的棋局使用当前两种模式及对应准备时限；不提供旧规则续赛。已结束的历史记录可查看和复盘，缺少模式元数据时不补造参赛约定。正常关闭服务会保存剩余准备时长，重启后继续倒计时，停服时间不计入准备；异常退出恢复到最近一次持久化的余额。已开始对弈的棋局按原流程暂停。

就绪后的等待属于参赛任务：棋手在当前会话循环调用 `arena_wait`，每次沿 `nextAfterSeq` 推进已读事件游标；等待超时后继续，收到开赛状态后按回合行动。对手尚未就绪或暂时没有活动是正常等待，不需要交回用户处理。房主没有代替棋手就绪的接口。此约定同时体现在规则结果、准备阶段的即时提示和工具说明中，具体操作流程见 Skill；`player.md` 继续只维护用户的棋手表达要求。协议能向仍在等待的调用返回开赛事件，不能唤醒已结束的 agent 会话，实际持续参与仍取决于客户端执行。

棋手通过随想让用户跟上即时的观察、判断和反应，尚不成熟的念头也可随时发送。每条一句，用自然语言而非内部代码或分析记号，提及位置时用 A1 这样的坐标；不因计时而省掉随想，也不要求每手固定条数。落子、认输和提和工具只提交动作，文字通过 `arena_note` 独立发送。观战使用自下向上推进的悬浮气泡：双方按事件顺序交错，共用一个滚动位置，新消息从底部出现，旧消息一起上移；每条消息的头像与名称在气泡外侧，黑方居左、白方居右。气泡上方标记关联局面的手数，未落子时显示“开局”，实际发送时间可在时间线中查看；以事件的 ply 为准，不随当前棋盘手数改写。气泡自然撑开，无内部滚动条；旧长消息完整换行，查看历史时新消息不抢走阅读位置。聚焦棋局和真实发言，不显示重复状态、等待占位、操作注释或绿色连接/回合小圆点。连接异常才显示提示，恢复后自动撤去。只适配横屏桌面浏览器（16:9、4:3）；不提供窄屏/移动布局。随想由棋手通过工具发送，服务不自动读取外部客户端的过程消息或 reasoning。浏览器可读所有随想和解说；各席位仅能在按需复盘中读取自己的发言原文，日常状态与等待不重复原文，解说员也不会收到棋手随想。旧棋谱中的 `speech` 事件继续显示，并适用同样的过滤。

解说员按真实手数发布评论，分析落后于棋局时明确关联旧手数。启动服务的 agent 可以领取解说邀请，在完成主持工作后转任解说；参赛者不同时扮演中立解说。

## 棋钟

棋手入席时收到的 `rules.clockRule` 和随后无路径参数的 `arena_rules.clockRule` 使用本局实际配置，写明每方初始时间、成功落子的加秒、计时起止与超时结果。不限时局明确返回不限时说明及 `clock: null`。规则说明中的初始额度与状态中的当前余额分别表达，重连后仍能查到本局最初约定。文字模板位于 `arena/prompts/rules.json` 的 `clock`，保留 `{{initial}}` 和 `{{increment}}` 占位符。

限时局中，时间是棋手的战略资源，操作 Skill 要求按余时调整思考深度、为后续回合与提交落子留余量，同时照常发随想。不限时局可持续分析和落子，棋手仍按回合跟进对局。

棋手状态包含 `guidance: {action, text}`；`action` 为 `prepare`（阅读规则并准备就绪）、`act`（本方回合，可落子或作其他决定）、`wait`（继续跟进）、`stop`（终局）。`text` 显示本方与对手的分秒余时、每步加秒和本方走钟状态；仅本方正在走钟且余时不超过 30 秒时提醒预留提交时间。不计时、未开赛、暂停和终局分别处理，不会提示已经停钟的棋手抢时间。非棋手视角为 `null`。它与 `clock` 使用同一快照，响应后不会自行刷新，也不写入棋局事件或替棋手发随想。加入和随想结果在 `state.guidance`，规则结果在顶层 `guidance`，其余状态结果在顶层；CLI 与两种 MCP 传输一致。全部提醒文案位于 `arena/prompts/status.json`。

开局面板直接提供三档预设（每方 5 分钟加每步 5 秒、15 分钟加 15 秒、30 分钟加 30 秒）和不限时。初始选中 5 分钟加 5 秒。四档切换保持面板布局固定。服务允许初始时间 1000–3600000 毫秒，加秒 0–60000 毫秒；浏览器按分钟/秒配置。棋钟在开赛后运行，仅扣当前行棋方时间；查规则、发送随想、等待工具和提和不暂停计时。落子只加一次秒，重复请求、非法落点与失败请求都不加秒。内置 AI 同样使用自己的棋钟。

`arena_state`、加入结果、动作结果、复盘、`arena_rules` 与 `arena_wait` 的 `clock` 返回双方 `remainingMs`、当前计时的 `active`、`deadline`、初始时间和加秒；随想结果中位于 `state.clock`。等待工具即使没有新事件也返回当时的余时。运行时 `serverNow` 表示快照时间，停钟时为 `null`，与 `deadline` 同为 Unix 毫秒时间戳。棋手依据快照与截止时间安排思考，工具响应之后仍继续走钟；接口不会中断客户端内部的模型生成。浏览器在本机按服务截止时间显示倒计时；判负由服务检查，不能依赖页面计时器。时间耗尽返回 `winReason: "timeout"`，对方获胜，棋盘保持原样；不需要任何一方再次调用工具，等待中的客户端和浏览器会收到终局事件。

等待开赛、房主暂停和终局停钟，恢复时不额外加秒。保存时记录当时余额，重启后棋局暂停，离线时段不扣时；异常退出最多恢复到最后一次持久化的余额。历史棋谱缺少棋钟时不补造计时记录。棋钟不改变随想的用途与发送时机。

## 棋手资料、尺寸与记录管理

首页复用原游戏大 logo，logo 在上、单行标题在下，整体垂直居中，不显示本地模式副标题或关卡大图案。对局顶部居中展示关卡名称与图案，不显示棋局名称。设置复用原游戏滑杆式图标：在首页的创建面板右上角，在对局的关卡名旁边；邀请、准备进度、暂停/继续、结束、时间线、棋谱导出和记录都在设置中。底部将棋局状态与当前手数合为同一行，放在两条加长、对齐的滑块上方；准备、暂停、行棋和终局结果直接显示在这里，不在设置中重复。复盘时同一位置显示回看手数与返回操作，不增减行高或推动棋盘。

创建前可点击双方头像配置显示名称和头像；对局中点击棋手身份或设置中的棋手资料继续编辑。默认头像为对应的黑棋或白棋，复用既有棋子材质。内置 DeepSeek、OpenAI、Claude、Gemini、Kimi、Qwen、Grok 七种标识，点击后将显示名称填为对应 AI 名称，用户可继续改成昵称；切回默认头像或上传图片不改当前名字。支持上传 PNG、JPEG、WebP（5 MB 以内），浏览器居中裁成方形并缩小为 PNG，保存在本机棋局记录。下一局沿用浏览器记住的资料。显示名与 agent 加入时的身份名分开保存，改名不会影响重新加入或撤销角色凭证。

棋盘宽高可分别设为 5–19 个交点；球面要求正方形，宽高联动。尺寸创建后固定，写入棋谱并在服务重启后保留。Arena 在自己的控制器实例中配置共享规则引擎，不修改共享关卡表或其他渠道。选手应始终以当前状态和规则工具返回的尺寸为准。

二维观战棋盘采用字母/数字轴标，文字棋盘、最近落子说明与时间线使用同一约定。已连接边的网格向外延伸半格至辅助线，未连接的边不延伸；通过共享绘图的可选 `extendGridToRails` 参数启用，不复制裁判或曲面实现。

坐标标签按各自所在边的连接情况定位。连接边的标注位于辅助线外，开放边按棋子外沿保留少量间距。这样开放边的标签更贴近网格，同时为边缘落子留出可读空间。

开局面板与弹窗复用共享 `app/assets/style.css` 的设置面板玻璃层及轻遮罩。换挡与连续滑条沿用游戏本体的透明滑块、折射轨道、运动曲线和回弹反馈。二维、三维、上一手和下一手图标复用 `app/index.html` 中对应工具按钮的路径。新随想到来时，旧消息和头像从当前画面位置平滑上移，连续到达时接续动画，用户滚动历史时保留阅读位置。视觉对照与交互验证见[视觉 QA](../design/qa.md)。

棋局记录显示本地日期时间、关卡、双方名字、状态与手数，终局直接显示黑方胜、白方胜、和棋或房主结束。超时与认输同时注明原因，可打开、结束或删除单局。清空只删除已结束棋局，进行中的棋局保留；结束、删除和清空均在界面中确认。删除会通知正在观看该局的窗口返回首页，服务重启后不会重新出现。

内置头像 SVG 来自 [Lobe Icons](https://github.com/lobehub/lobe-icons)，固定来源修订见 [source.json](../../arena/public/avatars/source.json)，保留 [MIT 许可](../../licenses/lobe-icons-LICENSE.txt)。这些标识用于用户自行标注棋手，不能作为实际模型身份的验证。资源随本地服务交付，使用时不访问外部图标服务。

## 认输与和棋

开赛后的任一选手均可认输，不受回合限制，暂停时也可决定。服务立即结束比赛，结果为对方胜、`winReason: "resign"`，取消后续内置 AI 落子，保留现有棋盘。无需继续到五连，也不要求附带解释。

提和返回 `drawOffer: {id, role, ply}`，需要另一位选手引用当前 `id` 接受或拒绝；提议方只能撤回。接受后结果为 `outcome: "draw"`、`winReason: "draw_agreement"`。任一方落子都会清除当前提议，同一选手在同一局面最多提和一次。提议、回应和认输均须携带最新 `expectedVersion` 与唯一 `requestId`；它们推进事件序号，不改变棋盘版本。重试时沿用完全相同的参数，服务重启后仍保持幂等。

内置 AI 自动回应提和：至少半盘已有棋子、双方均无一步获胜点，且双方可用五格路径数量较大值不超过较小值两倍时接受，否则拒绝。这是公开、确定性的规则，不生成模拟思考或话术。完整规则查询会返回该策略。

邀请传递本局信息、加入凭证与本地文件绝对路径，黑白棋手邀请另外直接附上最新 `player.md`，让用户发送的参赛消息本身包含棋手要求。全文只维护在 `player.md`，生成邀请时读取，不在模板中手抄第二份。agent 读取 Skill 获得操作流程；解说员邀请不附棋手要求，仍读取自己的角色文件。

修改棋手要求后，重新打开邀请弹窗即可复制最新全文，也可以让已入席的 agent 重新读取相应文件。已经发出的邀请和会话上下文不会随文件修改自动更新；MCP 服务简介和工具描述则在重新连接时读取。本地文件无法访问时应报告路径问题，不使用另一份 checkout 或猜测缺失的要求。

首次发行前的协议调整：`arena_note` 替代 `arena_speak`，移除 `kind`、`arena_move.explanation` 和认输/提和的 `reason` 字段。更新后重连 MCP 并重新读取 Skill；旧棋谱和气泡保留，旧调用参数不再接受。

这些文件改变的是说明，不改变裁判规则、参数校验或权限。MCP 参数 schema 位于 [tools.cjs](../../arena/tools.cjs)；状态、错误与结构化规则由 [match.cjs](../../arena/match.cjs) 产生，其中拓扑的 `edgeText`、`ruleText` 沿用共享 [level-config.js](../../app/assets/level-config.js)。它们也会出现在 agent 的工具结果中，不应与角色行为提示混淆。

## 运行边界与恢复

- MCP 提供工具，不保证 agent 会无限持续运行。参赛/解说 prompt 与 Skill 约定继续循环，但客户端的任务、预算、审批与会话寿命仍由客户端控制。
- agent 暂时断线不应抹去棋局。恢复后先读当前状态，校验身份与回合，再从已见事件序号继续。房主可暂停等待，不默认以一次网络超时判负。
- 同一电脑上的程序在操作系统层面可能读取同一用户文件；角色 token 用来约束正常接口，不构成面向恶意本机进程的安全沙箱。
- 模型账户、API key 与推理调用由各客户端管理，对弈室不收集模型 API key。“棋局本地运行”不表示云模型断网可用。
- 第一版不提供云端托管、自动唤醒已结束的客户端、语音合成或视频导出。比赛记录为以后的视频制作保留事件基础，不将该能力标成已完成。
