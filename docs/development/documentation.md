# 文档维护规则

文档是实现的一部分，不是功能完成后的可选补记。每项任务在开始时判断文档影响，在同一任务分支中更新，在预览和合并前一起验证。

## 信息归属

| 变化内容 | 必查文档 |
| --- | --- |
| 产品能力、玩法、关卡或平台状态 | 根目录 `README.md` |
| Agent 硬约束、完成标准或安全边界 | 根目录 `AGENTS.md` |
| 贡献步骤、验证矩阵或 PR 交接 | 根目录 `CONTRIBUTING.md`、PR 模板 |
| 分支、worktree 或日常任务合并流 | `docs/development/repository.md` |
| 维护者提升、冲突处理或平台整合 | `docs/development/merging.md` |
| 稳定版本、平台发布或统一版本规则 | `docs/development/release.md` |
| 命令、脚本、运行时、依赖或生成工具 | `docs/development/environment.md` |
| 色彩、材质、字体、动效或组件语言 | `docs/design/visual-language.md` |
| 视觉验收方法、视口、证据或已知限制 | `docs/design/qa.md` |
| 小红书容器、JSBridge 或 ZIP 规范 | `.codex/SKILL.md` 及其 references |
| Bilibili Toy / 微信小游戏宿主约束 | 对应发行分支的平台文档 |
| 新增、移动或删除任意长期文档 | `docs/README.md` 索引及全部反向引用 |

“必查”不等于每次都必须修改，但必须确认现有内容是否仍准确。若没有文档影响，在 Pull Request 中写明原因，不能只留空或默认忽略。

## 任务流程

1. **开始时**：根据上表列出本任务可能受影响的文档。
2. **实现时**：代码、测试、资源与文档在同一任务分支演进，不另开“以后补文档”的尾项。
3. **验证时**：运行 `npm run docs:check`；涉及代码和 H5 时运行 `npm run check`。
4. **预览时**：向用户或评审者同时展示行为结果和文档变化。
5. **合并前**：PR 的“文档影响”必须列出更新路径，或写明无影响及理由。

## 自动门禁

`npm run docs:check` 会检查：

- Markdown 内部链接目标是否存在；
- 是否残留本机用户目录或临时剪贴板路径；
- `docs/` 下的长期文档是否都被 `docs/README.md` 收录。

`npm run check` 包含文档校验，GitHub Actions 对 Pull Request 和长期分支运行该总检查。自动门禁只能发现结构性问题，不能判断内容是否语义过时，因此仍需完成上面的影响审查。

## 定期整理

在版本提升、平台里程碑或文档大改时做一次完整审计：

- 命令是否真实存在且可以运行；
- 分支、平台状态与目录结构是否仍准确；
- 设计证据文件是否存在，旧证据是否仍有保留价值；
- 是否存在重复、冲突或只记录历史调参过程的文档；
- 平台专属知识是否误放到共享分支。

过时内容应修正或删除，不通过追加“新说明”让相互矛盾的段落长期共存。
